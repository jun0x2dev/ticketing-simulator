# 좌석 선점자 확인과 토큰당 1석 제한

## 선택지

선점자 확인 (결제/해제를 누가 할 수 있는가)
1. 확인하지 않음: `seatId`만 알면 누구나 결제/해제할 수 있다.
2. 좌석에 입장 토큰 기록(`Seat.heldBy`): 결제/해제 요청의 `X-Entry-Token`과 비교한다.
3. 회원 인증 도입: 로그인 사용자 ID로 비교한다.

선점 수 제한
1. 제한 없음
2. Redis 토큰 단위 표시(`seat:holder:{token}`, `SET NX`, TTL 5분)
3. DB 조회: 선점 직전에 `heldBy = token`인 HELD 좌석이 있는지 센다

## 선택

- 선점자 확인: 2번. 좌석에 입장 토큰을 기록하고 결제/해제할 때 비교한다.
- 선점 수 제한: 2번. 토큰당 동시에 1석까지만 허용하고, Redis 토큰 표시를 좌석 락보다 먼저 건다.

## 이유

- 이 프로젝트에는 회원이 없고, 대기열을 통과한 사람을 구분하는 수단은 입장 토큰 하나다. 인증(3번)은 MVP 범위 밖이라, 이미 있는 토큰을 선점자 식별자로 쓴다.
- 확인하지 않으면 남의 좌석을 결제할 수 있다. Mock 결제가 거절되면 남의 좌석을 풀어 버릴 수도 있다. 또 TTL이 지나 다른 사람이 다시 잡은 좌석을 원래 사용자의 늦은 결제가 확정해 버린다. 이 마지막 경우는 `confirmSeat`이 행 잠금 뒤에 `heldBy`를 다시 확인해서 막는다.
- 선점 수를 제한하지 않으면 대기열을 통과한 한 명이 좌석을 모두 쓸어 담을 수 있다. 그러면 대기열로 만든 공정성이 의미가 없어진다.
- DB로 세면(3번) 같은 토큰으로 동시에 들어온 두 요청이 둘 다 "0석"을 보고 통과할 수 있다. 막으려면 별도 잠금이 필요하다. Redis `SET NX`는 한 명령으로 원자적이고, 좌석 락과 같은 방식·같은 TTL이라 만료 처리도 따로 필요 없다.
- 감수한 점:
  - 제한은 "동시에 1석"이다. 확정하거나 해제한 뒤에는 토큰이 살아 있는 동안(10분) 다른 좌석을 다시 잡을 수 있다. 1인 구매 매수 제한이 필요해지면 확정 수를 따로 세야 한다.
  - Redis 표시 삭제는 DB 커밋 전에 일어난다. 커밋이 실패하면 표시만 먼저 사라질 수 있지만, 좌석은 HELD로 남아 TTL 복구가 정리한다.
  - 사용자가 직접 해제한 경우(`/seats/{id}/release`)에는 `seat.released`를 Kafka로 발행하지 않는다. 통계는 결제 거절과 TTL 만료만 센다. 좌석 화면은 WebSocket 브로드캐스트로 갱신된다.
