# 예매 취소는 환불 먼저, 예매 취소 반영은 그다음

## 선택지

처리 순서
1. DB 먼저: 결제를 `REFUNDED`로 바꾸고 좌석을 다시 연 뒤 커밋하고, 그다음 게이트웨이에 환불을 요청한다
2. 환불 먼저: 게이트웨이 환불이 성공한 뒤에 한 트랜잭션에서 결제 `REFUNDED`, 좌석 재오픈, `seat.released` 기록을 반영한다

취소 요청자 확인
1. 좌석의 선점자(`held_by`)로 확인한다
2. 결제 기록에 결제한 사용자의 입장 토큰(`payer_token`)을 남기고 그것으로 확인한다

## 선택

- 처리 순서는 2(환불 먼저)
- 요청자 확인은 2(`payer_token`)

## 이유

- 두 방식 모두 "환불"과 "DB 반영" 사이에서 실패할 수 있다. 차이는 실패했을 때 사용자가 무엇을 잃느냐다.
  - DB 먼저: 커밋 뒤 환불이 실패하면 좌석은 이미 남에게 열렸는데 돈은 돌려받지 못한다. 결제가 `REFUNDED`라 사용자가 다시 취소할 수도 없다.
  - 환불 먼저: 환불이 실패하면 아무것도 바뀌지 않아 예매가 그대로 남고, 사용자가 다시 시도할 수 있다. 환불 뒤 DB 반영이 실패하면 돈은 돌려받았는데 좌석이 남는다. 이 경우는 결제 ID와 승인 번호로 error 로그를 남겨 수동으로 맞춘다.
- 외부 호출(환불)이 실패하는 경우가 DB 커밋이 실패하는 경우보다 훨씬 흔하다. 흔한 실패에서 사용자가 손해를 보지 않는 쪽을 골랐다. 기존 결제 흐름의 "승인 후 확정 실패 시 승인 취소"도 게이트웨이 호출 후 기록하는 같은 순서다.
- 환불은 트랜잭션 밖에서 부른다. 게이트웨이 지연 동안 DB 커넥션과 행 잠금을 잡고 있지 않기 위해서다.
- 같은 예매의 취소가 동시에 오면 환불이 두 번 나갈 수 있다. 결제와 같은 좌석 락(`payment:lock:{seatId}`)을 잡고, 락 안에서 결제를 다시 읽어 `SUCCESS`인지 확인한 뒤에 환불한다. 트랜잭션 안에서는 결제를 행 잠금으로 한 번 더 확인해, 락 TTL이 지난 극단적인 경우에도 두 번 반영되지 않게 한다.
- 좌석은 확정될 때 선점자 정보(`held_by`)가 지워진다. 그래서 좌석으로는 누가 결제했는지 알 수 없어 결제 기록에 토큰을 남겼다. 입장 토큰은 Redis에서 10분 뒤 만료되지만, 취소는 저장된 값과 비교만 하므로 토큰이 만료된 뒤에도 본인 확인이 된다.
- 감수한 점: 사용자 인증이 없어 입장 토큰이 곧 예매 증빙이다. 토큰을 아는 사람은 그 예매를 취소할 수 있다(README의 남은 과제와 같은 한계). 공연 시작 이후 취소 금지, 취소 수수료 같은 정책은 시뮬레이터 범위 밖이라 넣지 않았다.
