# 대기 순번 계산: Redis Sorted Set

## 선택지

- Kafka 오프셋으로 계산 (내 메시지 오프셋 - 컨슈머 커밋 오프셋)
- Redis Sorted Set에 접수 순서를 따로 기록 (`ZRANK`)
- 순번을 WebSocket으로 모든 대기자에게 주기적으로 브로드캐스트 vs 클라이언트가 폴링

## 선택

입장 요청 시 Kafka 발행 전에 `queue:line:{eventId}`(Sorted Set, score = INCR 순번)에 넣고, 입장을 허용하면 뺀다.
순번은 상태 조회(`GET /events/{eventId}/entries/{requestId}`) 때 `ZRANK`로 계산하고, 클라이언트가 1초마다 폴링한다.

## 이유

- Kafka 오프셋 방식은 파티션이 3개라 같은 이벤트라도 키 기반 파티션 하나만 보면 되지만, 프로듀서 응답에서 오프셋을 받아 요청별로 저장하고 컨슈머 그룹 lag을 조회해야 한다. Admin API 호출이 폴링마다 생겨 비싸고 복잡하다.
- Sorted Set은 `ZRANK`/`ZCARD`가 O(log N)/O(1)이라 폴링 비용이 작고, 줄에서 빼는 것만으로 순번이 당겨진다. 이미 Redis를 쓰고 있어 인프라도 늘지 않는다.
- 순번을 서버에서 브로드캐스트하려면 대기자마다 다른 값을 주기적으로 보내야 해서, 대기자가 많을수록 메시지 수가 늘어난다. 각자 1초 폴링이 단순하고 부하도 예측 가능하다. 입장 허용 자체는 기존대로 WebSocket으로 즉시 알린다.
- Kafka 발행 전에 줄에 세우는 이유: 반대로 하면 컨슈머가 먼저 처리해 줄에서 뺀 뒤에 줄에 들어가 영원히 남는 요청이 생길 수 있다.
- 감수한 점: Redis 순번(INCR)과 Kafka 실제 처리 순서가 동시 접수 시 미세하게 다를 수 있다(표시용이라 허용). 예상 대기 시간은 설정 TPS 기준이라 실제 처리 속도(측정 시 초당 약 16명, 설정 20)보다 약간 짧게 나온다. DLT로 빠진 요청은 줄 키가 만료될 때까지(마지막 접수 후 1시간) 순번에 남는다.
