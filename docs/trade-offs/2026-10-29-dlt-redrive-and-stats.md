# DLT 재처리 방식과 통계 집계 저장소

## 선택지

- DLT 재처리: (a) 로그만 남김 (b) 관리자 API로 수동 재처리 (c) DLT Consumer가 지연 후 원래 토픽으로 자동 재투입 + 횟수 제한 후 최종 실패 처리
- 통계 저장소: (a) MySQL 집계 테이블 (b) Redis Hash 카운터
- 통계 멱등성: (a) 중복 확인 키와 카운터를 별도 명령으로 (b) Lua 스크립트로 원자적으로

## 선택

- DLT: (c). 도착 5초 뒤 1회 재투입하고, 재투입본까지 실패하면 대기 줄에서 빼고 `FAILED`로 표시한다.
- 통계: Redis Hash + Lua 스크립트(SET NX + HINCRBY).

## 이유

- 입장 요청 실패의 흔한 원인은 Redis/네트워크의 일시적 장애라 한 번 더 시도하면 대부분 복구된다. 수동 재처리는 대기 중인 사용자가 기다릴 수 없어 맞지 않는다. 횟수를 1회로 제한하고 메시지에 `redriveCount`를 실어 무한 순환을 막았다. 재투입해도 requestId가 같아 토큰 발급 멱등성이 그대로 적용된다.
- 최종 실패를 표시하지 않으면 사용자는 순번이 멈춘 화면에서 계속 기다린다. 실패를 알려 다시 줄 서게 하는 편이 낫다.
- 지연은 메시지 도착 시각 기준으로 남은 시간만 기다린다. 장애로 DLT가 밀려 있으면 오래된 메시지는 바로 처리한다. 감수한 점: DLT Consumer 스레드가 잠드는 동안 다른 DLT 메시지도 기다린다(DLT는 실패 메시지만 오므로 양이 적다).
- 통계는 카운터 증가만 하므로 Redis Hash가 MySQL보다 가볍고 행 잠금 경합이 없다. 회차와 같이 단기 데이터라 TTL로 정리된다. 감수한 점: Redis가 날아가면 통계도 사라진다(시뮬레이터 통계라 허용).
- 중복 확인과 증가를 따로 하면 그 사이에 실패할 때 "확인만 되고 안 세짐"이 생긴다. Lua 스크립트로 묶어 원자적으로 처리했다. 두 키가 다른 해시 슬롯이라 Redis Cluster에서는 해시 태그가 필요하다(현재 단일 노드).
- 하위 Consumer(통계, WebSocket 릴레이)의 DLT는 메시지를 보관만 한다. 통계 한 건이 빠지는 것은 사용자 흐름에 영향이 없어 재처리하지 않았다.
