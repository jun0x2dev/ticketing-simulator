# 오픈 시각 전에도 입장 요청이 접수되고 토큰이 발급됨

## 증상

- `openAt`이 하루 뒤인 회차에 `POST /api/v1/events/{eventId}/entries`를 보내도 202로 접수되고, 잠시 뒤 입장 토큰이 발급됐다. `entries/direct`도 바로 토큰을 줬다.
- 티케팅의 전제는 "정해진 시각에 모두가 같은 출발선에 선다"인데, 오픈 전에 미리 줄을 서거나 토큰을 받아 좌석을 먼저 잡을 수 있었다.
- k6 시나리오는 이 구멍에 기대고 있었다. 이벤트를 이틀 뒤 오픈으로 만들고 바로 입장 요청을 보냈다.

## 원인

- 입장 서비스가 이벤트 존재만 확인하고 `openAt`은 보지 않았다.
- 이벤트 생성 API가 `openAt`을 시간대 없는 `LocalDateTime`으로 받았다. k6(UTC 컨테이너)가 보낸 시각을 서버(KST)는 자기 시간대 시각으로 해석해 실제 순간이 의도보다 9시간 이르게 저장된다. k6가 이틀 뒤로 잡은 것도 이 어긋남 때문에 `@Future`에 걸리지 않게 하려는 우회였다. 오픈 검증을 넣으면 이 우회가 그대로 "이틀 가까이 열리지 않는 회차"가 되고, "몇 초 뒤 오픈"으로 바꾸면 9시간 전 시각으로 읽혀 `@Future`에 걸린다.

## 해결

- `EntryServiceImpl`이 두 입장 API(`entries`, `entries/direct`) 모두에서 서버 시각이 `openAt` 전이면 `EVENT_NOT_OPENED`(409)로 거절한다. 줄에 세우거나 발행하기 전에 확인하므로 거절된 요청은 아무 흔적도 남기지 않는다. 클라이언트 시계는 조작할 수 있으므로 서버 시각으로만 판단한다.
- `EventCreateRequest.openAt`을 `OffsetDateTime`으로 바꿔, 오프셋이 있는 시각(`...Z`, `...+09:00`)만 받는다. 서비스가 같은 순간의 서버 시간대 시각으로 바꿔 저장하므로 오픈 검증과 회차 정리가 서버 시각 하나로 맞춰진다. 오프셋 없는 시각은 400이다.
- k6 setup은 3초 뒤 열리는 이벤트를 UTC로 만들고, 오픈 1초 뒤까지 기다린 다음 가상 관객을 한꺼번에 보낸다. "오픈 직후 N명이 동시에 몰림"을 그대로 재현한다.
- 화면의 회차는 만드는 즉시 열리므로(오픈 시각 = 현재 서버 시각) 사용자 흐름은 바뀌지 않는다.
- `EntryServiceImplTest`에 오픈 전 거절 테스트 2건, `EventServiceImplTest`에 시간대 변환 테스트를 추가했다. 수정 전 코드에서는 오픈 전 요청이 그대로 접수되어 실패한다.
